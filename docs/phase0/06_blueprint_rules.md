# 06. Blueprint Rules (обязательные)

Этот файл — обязательные правила для всех следующих фаз.

## 1) Cast rules

### 1.1 Когда Cast разрешен
Cast допустим только если одновременно выполняются условия:
1. Нельзя решить задачу через Interface / базовый тип.
2. Тип нужен для конкретной API, доступной только в этом классе.
3. Cast делается в контролируемой точке (инициализация, BeginPlay), а не спамится в Tick/каждый input event.

### 1.2 Когда Cast запрещен
- В каждом кадре (`Tick`) без острой причины.
- В каждой input-событии, если ссылку можно закешировать один раз.
- В UI-логике для доступа к геймплейным данным (использовать интерфейсы/dispatchers).

### 1.3 Предпочтения по порядку
1. Interface
2. Базовый тип (`Actor`, `Pawn`, `Character`) + функции базового типа
3. Cast (последний вариант)

## 2) Кэширование ссылок
- Если ссылка нужна регулярно, получай и валидируй ее один раз в `BeginPlay`.
- Храни в переменной компонента/актора.
- На вызовах делай `IsValid` вместо повторного Cast.

## 3) SRP для компонентов
- Один компонент = одна зона ответственности.
- `BPC_PlayerControl` отвечает только за управление вводом/движением команды.
- Не добавлять в него боевую, инвентарную, квестовую логику.

## 4) Транзакции и rollback
- Для многошаговых операций (inventory/equipment/ability/status) используй шаблон:
  `Validate -> Reserve -> Apply -> Confirm`.
- При ошибке возвращай доменный fail reason (`E_OpFailReason`), а не `bool` без контекста.
- Если операция оборвалась после частичного применения — обязателен compensating rollback.

## 5) Частые обновления
- Не использовать бессмысленный `Tick`.
- Частые апдейты вести через:
  - таймеры с контролируемым интервалом,
  - event-driven обновления,
  - bucketed scheduler для массовых periodic задач.

## 6) Новые правила в фазах
Если добавляется новое правило, его нужно:
1. Записать в этот файл.
2. Обновить затронутые пошаговые инструкции.
3. Проверить чеклист фазы на соответствие.
